# Crystal Pool v0.1 — Issue Backlog

> This file lists every GitHub Issue needed to ship v0.1 (the minimal viable pool — core 12 mechanisms).
>
> Once the repository is created on GitHub, these become real issues. Until then, they live here as the canonical work breakdown.

---

## Conventions

- Each issue has: **Title**, **Acceptance Criteria** (what "done" means), **Constitution / Architecture refs**, **Depends on**, **Priority** (P0 = blocker, P1 = required, P2 = should-have).
- An issue is **not started** until its dependencies are merged.
- All v0.1 issues are required for v0.1; nothing here is optional.

### #8 — Decay & Bequest engine (P0) ⭐ core mechanism

**Acceptance**:
- `lib/crystal-graph/decay.ts` exports `applyDecay(node, dt)` — pure function
- Decay rate: `score *= exp(-k * dt)` where `k` is configured per phase (high `k` for fossil, low for high-ha nodes)
- `dissolveAndBequeath(node)` — when score ≤ threshold, node enters `dissolved`, its outgoing edges and ha are redistributed to top-2 strongest neighbors weighted by edge weight
- Unit tests:
  - High-ha node decays slower than fossil node given same baseline
  - Dissolved node's edges show up on neighbors with reduced weight
  - Decay is deterministic given fixed `dt` and inputs

**Refs**: Architecture Part V §2 (core 12), V0.1.

**Depends on**: #5, #6, #7.

## Phase 4 — Cluster Read Model (3 issues)

### #18 — `deriveMeaningClusters()` core function (P0)

**Acceptance**:
- `lib/meaning-clusters/derive-clusters.ts` — pure function with stable input shape
- Input: `{ nodes, edges, tags, phaseEvents, contributionEvents, marketOrders }`
- Output: `MeaningClusterSnapshot[]` per spec in Part XII of architecture
- Each snapshot includes: `clusterId`, `tagIds`, `nodeCount`, `edgeCount`, `avgScore`, `scoreMomentum`, `supportPressure`, `challengePressure`, `verificationDepth`, `dominantPhase`, `phaseDistribution`, `signalPrice`, `topNodes`, `recentContributionEvents`, `tideInflow`, `marketSignalRatio`, `whaleConcentration`, `diversityIndex`, `haTension`

## Phase 5 — Body, Trauma, Pool-rhythm minimal layers (5 issues)

### #21 — The Body Knows: per-actor inference override (P0) ⭐ core mechanism

**Acceptance**:
- Schema: `BodyInferenceVeto` with `id`, `actorId`, `inferenceKind`, `vetoedAt` (private — only readable by the actor)
- Service: `vetoBodyInference(actor, kind)` records veto AND lowers the system's confidence threshold for that kind for that actor by 10% (multiplicatively, capped)
- The confidence threshold per actor per kind is **only** used in subsequent inference for that actor — never aggregated, never published

- Body data ingestion (rates, environment light) is stubbed in v0.1 — only the override mechanism is implemented

**Refs**: Constitution §4.3, Architecture Part V §10 (core 12).

### #22 — Asymmetric Undo (challenge 30d, support 24h) (P0) ⭐ core mechanism (升入 v0.1)

**Acceptance**:
- `revokeContributionEvent(event, actor)` rules:
  - `challenge` events: free revoke ≤ 30 days from creation
  - `support / verify / build_intent`: free revoke ≤ 24 hours
  - `judgment-free` content (placeholder for v0.2 — flag in v0.1): always editable by author
  - Outside these windows: cannot revoke
- Revoke creates an audit row, freezes weight at that moment (per #17)
- Sanctuary-period reverse-immune: any challenge submitted while target was in `sanctuary` phase **is auto-flagged** with `requires_resubmission` so it doesn't fully apply (the flag is fully wired in v0.2; in v0.1 the flag exists and is recorded)
- Unit tests for each window boundary

**Refs**: Constitution §4.5, Architecture Part XII ν-B5 (升入 v0.1 核心).

## Phase 6 — Exit & Audit layers (3 issues)

### #26 — Three-Tier Departure: Pause / Withdraw / Erase (P0) ⭐ core mechanism

**Acceptance**:
- **Pause**: actor flag `paused` ; data retained; tideBudget refill paused
- **Withdraw**: actor flag `withdrawn`; nodes + reputation transfer to a Trustee actor (Trustee mechanism is a stub in v0.1 — single text field "trusteeActorId"); 30-day reversible window
- **Erase**: actor flag `erased`; identifying metadata (email, display name, profile body) cryptographically nulled; nodes and contribution events retained but `actorId` becomes a stable opaque hash; 90-day cooling-off period before final
- All three are user-initiated; no admin action can trigger them
- Unit test: after Erase, `Actor.findById()` returns the stub but no PII; PhaseEvent / ContributionEvent rows remain queryable

**Refs**: Constitution §2.5, Architecture Part V §11 (core 12).

**Depends on**: #5, #10.
